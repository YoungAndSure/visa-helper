# Visa Helper 产品方案：一次申请的完整流程助手

> 状态：产品方向稿。首个支持的签证场景、官方规则和商业模式仍需验证。
>
> 本文描述新的产品目标与建设顺序。旧方向原型已移至 `archive/`，不代表新 App 的目标架构。

## 1. 产品方向

Visa Helper 是面向个人 DIY 旅游签证申请者的 App。首版以 ChatGPT 中的 MCP Apps UI 呈现，由 MCP Server 管理申请状态和业务规则。用户为一次具体的签证申请建立申请项目，App 根据其情况引导其完成从确认申请路径、准备材料、填写信息、制作辅助文件、检查材料，到预约与递交前准备的整个过程。

产品的核心对象是**一次申请**，而非一份待检查的文件或某个官方网页上的表单字段。用户进入 App 后，应该始终知道当前申请处于什么阶段、下一步做什么、哪些事项需要本人在官方渠道完成。

旧方向以材料审查和官方网页填表侧边栏为入口，介入较晚，难以管理申请全过程。新方向将材料审查和填表辅助纳入申请流程中的具体步骤。产品首先验证一条完整申请路径能否真正帮助用户完成准备，再扩展到其他签证场景。

## 2. 目标用户与产品边界

初期服务自行申请旅游签证、缺乏经验且希望减少查阅官方说明和重复填写时间的个人用户。第一条开发路径选择中国护照、居住中国、赴冰岛旅游；正式适用范围还需核实签证类型、受理渠道和其他条件。不能仅凭出发地和目的地推断要求。

App 负责：

- 判断用户是否落在已支持的申请路径内，并解释判断依据。
- 将适用的官方要求转化为可执行的步骤和材料清单。
- 采集、复用并让用户确认申请信息。
- 辅助理解申请表字段，制作允许由申请人自行准备的文件。
- 检查材料完整性、关键信息一致性和明显的日期逻辑问题。
- 汇总待完成事项，指引用户进入官方预约和递交流程。

App 不保证获签，不替代使领馆进行资格认定，不伪造银行流水、雇主证明等第三方原始文件，也不代替用户完成必须本人操作的身份核验、预约或正式递交。超出支持范围或规则无法确认时，App 应明确停止个性化指引，并提供官方来源供用户核实。

## 3. 一次申请的用户旅程

### 3.1 创建申请与确认路径

用户输入国籍、居住地、目的地、出行目的、预计日期及其他影响适用规则的必要信息。系统先判断是否支持该组合，再展示签证类型、受理渠道、主要步骤和官方依据，交由用户确认。无法确定适用路径时，不生成看似确定的清单。

### 3.2 建立申请计划

App 根据已确认的路径生成申请项目，包括步骤、材料、前置条件和需要用户在外部完成的事项。每一步显示完成条件、官方来源及最近核实时间。用户可以离开并恢复进度；规则更新时，已创建的申请应能识别受影响的步骤并提示重新确认。

### 3.3 采集信息与准备材料

用户逐步填写个人、护照、工作或收入、出行等信息，并上传已有材料。App 可以通过 OCR 或文件理解提取字段，但提取值必须由用户确认后才能用于正式文件或自动填表。关键字段保留来源、确认状态和最后修改时间。第三方出具的证明由用户准备，App 只说明要求和检查可验证的部分。

### 3.4 填表与制作文件

已确认的信息在申请项目内复用。填表辅助区分两种形态：

- **静态 PDF 表格**：在 MCP 服务中针对表格预先维护 HTML 模板、字段映射和填写说明。任务执行时，用已确认资料预填网页，未知项给出说明，返回独立网页链接，供用户对照填写原 PDF 或打印手写。后续逐步优化模板版式，使其更接近原表；不要求先实现直接编辑 PDF。填完后可选择自查或自愿上传辅助检查。
- **官方网站在线申请**：使用独立的浏览器引导流程，根据当前页面状态提供逐字段指引；是否辅助操作取决于客户端能力和用户授权。账号登录、动态页面和流程推进需单独设计验证，不承诺自动提交。

字段含义不清楚时提供来源明确的解释与示例。App 还可以生成 cover letter、行程说明等适合由申请人制作的辅助文件，并要求用户预览确认。

### 3.5 最终检查与交付

递交前检查包括必填信息、材料齐全性、跨文件字段一致性、日期逻辑和已结构化的官方要求。结果分为“已通过”“需修改”“待人工确认”“无法验证”，每个问题说明依据、涉及的文件或字段以及下一步操作。最终交付申请文件、材料清单、待打印或待上传事项、未解决风险和官方预约递交入口。用户完成官方递交后，可手动记录申请状态和结果，用于自己的进度管理。

## 4. App 的核心界面

| 界面 | 用户要完成的事 |
| --- | --- |
| 申请首页 | 查看当前申请阶段、下一步、未解决问题和截止事项 |
| 路径确认 | 核对适用的签证路径、支持边界及官方依据 |
| 步骤工作区 | 按顺序完成信息、材料和外部操作任务 |
| 信息与文件 | 查看已确认字段、来源、上传材料和生成文件 |
| 递交前检查 | 逐项处理错误、待确认项并导出交付包 |

交互以任务和进度为主，问答用于解释具体问题。用户始终可以返回修改已填信息；修改关键字段后，相关文件和检查结果必须标记为需要重新生成或复核。

## 5. 产品与数据模型

核心实体建议从以下几项开始：

- **Application**：一次申请的身份、适用路径、阶段、创建时间和所使用的规则版本。
- **Applicant Profile**：本次申请需要的结构化字段；关键字段记录来源、提取方式、用户确认状态和更新时间。
- **Task**：当前路径中的一个可执行步骤，含完成条件、依赖关系和状态。
- **Document**：用户上传或系统生成的文件，含类别、关联任务、版本及处理状态。
- **Rule**：适用条件、材料要求、字段约束和例外，含官方来源、适用范围、版本、核实日期和维护责任人。
- **Validation Result**：检查对象、规则、结果、证据与处理状态。
- **Feedback**：用户在具体申请、步骤和规则上报告的问题；作为调查线索，不直接成为官方规则。

申请、规则和工作流版本应能关联。规则变更后，应能判断哪些进行中的申请受到影响。删除申请时应删除相应个人资料及文件，并向用户说明实际处理范围。

## 6. 实现原则

### 6.0 ChatGPT 宿主与服务端职责

ChatGPT 提供对话入口和解释能力；MCP Apps UI 展示表单、进度和操作按钮，并能通过宿主直接调用 MCP 工具；MCP Server 是申请状态、步骤顺序、适用条件与校验结果的唯一权威。Agent 或 UI 都只能请求操作，不能绕过服务端规则推进流程。申请进度保存在服务端，不依赖对话上下文或 iframe 的临时状态。首版仍需为接入 ChatGPT 解决服务端认证和申请所属关系，之后才能处理真实个人材料。

### 6.1 规则、流程与组件分离

规则回答“这个场景要求什么”，流程回答“用户按什么顺序完成”，组件负责“如何采集、展示、检查或生成”。不同场景共享护照信息采集、文件上传、任务进度、字段确认和检查展示等能力。只有在第二条实际路径出现后，才根据已观察到的差异抽象声明式流程配置；第一条路径不预先建设覆盖所有国家的通用引擎。

### 6.2 确定性优先，AI 辅助

适用路径、必填项、日期计算、字段映射和材料完整性尽量由可测试的规则实现。AI 用于非结构化文件提取、字段解释、辅助写作和异常分析。AI 提取的值不得直接覆盖用户已确认的信息；AI 生成的文字不得被呈现为未经核实的官方要求。

### 6.3 规则来源与失效处理

每条影响用户行动的规则应指向可核实的官方来源，并记录适用条件、最近核实时间与版本。官方页面或表格变化、来源不可用、规则超出核实周期，均应触发人工复核。复核前，受影响的步骤应显示待核实状态；对关键适用性判断不能继续给出确定性结论。用户反馈可以触发调查，规则发布仍需依据可靠来源审核。

### 6.4 个人资料处理

只收集当前申请所需信息，限制原始材料的持久化和第三方传输；向用户说明哪些处理使用第三方服务。日志不得记录护照号码等敏感字段。上传、临时处理、保存、导出和删除都需要明确的数据边界。恢复申请进度与减少持久化之间的取舍，应在 MVP 存储方案中明确，而不能沿用旧后端“完全无状态”的假设。

## 7. 首个版本：单路径端到端 MVP

首个具体场景尚未确定。在选择前，记录该路径的完整适用条件、官方资料、申请表形态、可生成文件及实际递交方式。优先选择官方资料可核实、流程相对稳定、能接触到真实 DIY 用户的旅游签证场景。

MVP 必须让受支持用户完成一次申请准备的闭环：

1. 创建申请，确认自己属于支持范围。
2. 获得有来源的个性化步骤和材料清单。
3. 填写并确认关键资料，上传必要材料，保存进度。
4. 完成该路径必需的填表辅助和文件制作。
5. 查看递交前检查结果，处理错误或标记待人工确认。
6. 导出交付包，进入官方预约或递交环节。
7. 在具体步骤反馈问题。

OCR、自动填表和文件生成只实现该路径实际需要且能验证正确性的部分。若某步骤不能可靠自动化，应提供清晰的人工操作指引。MVP 不包含多国覆盖、官方站点自动操作、Agent 自动改规则、社区或复杂付费系统。

通过真实用户试用评估：支持范围内的用户能否完成准备；在哪一步退出或求助；准备耗时；人工复核发现的关键错误；用户是否理解检查结论；哪些能力产生明确付费意愿。获签结果可以记录，但不能单独作为流程正确性的证明。

## 8. 后续建设

第二阶段增加第二条实际申请路径，验证哪些组件可复用，再完善条件分支、声明式配置、规则版本管理与回归测试。衡量新增路径的人工建设时间、特殊处理量和用户错误率。

第三阶段让 Agent 辅助检索官方资料、生成规则或流程草案、检测来源变化、归类反馈和生成测试用例。草案必须可追溯并经人工审核后发布。

长期才探索基于官方变化和用户反馈的流程改进闭环。用户反馈属于异常信号，不自动修改签证规则。

## 9. 对现有仓库的影响

新产品以 ChatGPT 内的 MCP Apps UI 承载申请项目和完整旅程，MCP Server 执行流程。现有代码可以提供局部经验，但不应决定新架构：

| 现有模块 | 新方向中的处理 |
| --- | --- |
| `archive/audit/` | 借鉴清单提取和检查经验，将审查能力纳入申请末端；现有文件名匹配与单场景硬编码不能直接充当通用规则层。 |
| `archive/extension/` | 官方网页伴行交互可留作以后探索；首版入口改为 ChatGPT 内的 MCP Apps UI。 |
| `archive/form/backend/` | 可借鉴提取、脱敏和字段建议逻辑；本地 PDF 路径接口、无状态设计和面向扩展的 API 需要按 MCP 应用的上传与申请持久化流程重新设计。 |

旧原型不需要立即删除。新代码以 Application 为核心建立边界，再有选择地迁移可验证的能力，避免将旧模块的假设带入新产品。

## 10. 待决策事项

- 首条申请路径的完整适用条件和官方资料来源。
- MCP Server 的部署方式、ChatGPT 用户认证与申请所属关系。
- 哪些文件必须在 App 内生成，哪些只需引导用户在官方渠道完成。
- 规则复核周期、责任人和过期后的产品行为。
- 首批真实试用用户来源，以及完成率、错误率和时间节省的基线。
- 收费点和价格，待使用数据与访谈验证后确定。
