# 冰岛旅游签证：问答决策树与材料任务队列

> 状态：用于申请准备和流程测试；材料规则尚待按现行官方要求复核。
>
> 唯一材料依据：用户提供的《VISA DOCUMENT CHECKLIST – TOURISM / 签证材料审核表 – 个人旅游》，PDF 创建于 2025-03-06，共 4 页。下文的编号对应原表第 1–13 项。正式服务真实申请人前，须按 [来源核对记录](iceland-source-audit.md) 复核当前官方版本、受理地点和规则。
>
> 引擎实现：2026-10-17 的 0.5.0 已迁移为 XState 5.33.2，提供显式模型、决策图导出和结构化输入回放。材料条件保持原审核表版本的既有行为。

## 1. 两个阶段

**第一阶段：确定任务。** 用户通过对话回答决策树中的问题。MCP 服务端根据已确认的答案，生成这位申请人的材料任务队列。这个阶段只决定「需要准备什么」，不负责收集、填写或生成文件。

**第二阶段：完成任务。** 用户从队列中逐个进入材料处理流程。每个任务对应一个要准备的文件；处理流程可以复用，例如上传并核对现有文件、指导用户取得第三方证明、辅助填写表格或生成行程文件。任务完成时关联一个最终文件。具体处理方式后续单独设计，不写进决策树。

用户体验按以下顺序展开：

1. **对话启动**：用户表达申请意图后，GPT 调用 `advance_application`，首次提交空问答，取得申请 ID、完整问题目录和选项。简短说明可跟随提问或直接描述整段计划。问答仅在聊天中进行，不打开 MCP App 问卷。
2. **推进决策树**：GPT 将用户逐次回复或整段描述整理为同一个完整问答结构，每次提交完整快照及最新 `revision`。服务端校验、保存，从入口运行到缺少必要信息的位置或终点，返回 `nextAction`。
3. **补充分支问题**：GPT 优先使用用户已经明确给出的信息，包括后续分支答案，不重复询问。`ask` 返回当前问题与选项；没有答案时再问用户。修改早先答案后重走模型，下一题可以改变。
4. **修正和澄清**：`repair` 返回格式错误且整批未保存；已有事实足以明确编码时 GPT 自行修正后重交。`clarify` 用于业务矛盾或版本冲突。未知不等于否，不为满足分支篡改事实；规则定义是否走默认出口。详细字段和处理约定见[完整问答协议](interview-protocol.md)。
5. **终点展示任务队列**：服务端返回 `complete` 和只读清单展示动作；GPT 执行该动作才加载 MCP App 工作台。工作台自动关联申请，不要求再次创建或输入 ID 恢复。聊天仅简短指引点击材料，不重复清单。宿主把 UI 模板绑定在工具声明上，因此展示动作独立于唯一的问答推进接口。
6. **逐项完成任务**：用户从队列选择任务，进入该材料的独立处理流程；完成后把文件关联回原任务。更改分支答案时重新计算队列，并提示新增、移除及需复核的任务。
7. **递交前总览**：按原表顺序展示已完成、待处理及需人工确认的任务。第 3–4 页的签字／补件须知是递交阶段事项，不在材料筛选时误当成文件任务。

首版固定为**一位申请人对应一份申请和一份个人清单**。同行者的申请不进入本轮流程。

## 2. 问题树与材料分支

| 问题组 | 一次展示的问题 | 对清单的影响 |
| --- | --- | --- |
| 基础 A：路径 | 国籍；是否居住中国及拟递交城市；是否为旅游；是否还去其他申根国家及各国停留日期 | 决定是否进入本模拟路径；多国行程触发第 5 项的跨国交通材料，并提示核对冰岛是否为主要目的地。递交城市不从这份 PDF 推断具体受理中心。 |
| 基础 B：行程与申请人 | 首次进入／离开申根区的日期；出行时是否未满 18 岁；同行人员 | 日期供第 2、4、7 项检查；年龄决定进入成人或未成年人补充组。 |
| 成人 C：职业 | 在职、退休、无业？ | 第 11 项进入对应子分支。这里不能只问「是否有工作」，否则无法区分退休与无业。 |
| 成人 D：无业时 | 已婚／单身／离异／丧偶？旅行费用及日常收入来自哪里？由配偶、其他担保人还是本人承担？ | 已婚且依赖配偶、单身／离异／丧偶有固定收入、非配偶担保分别对应原表第 11 项的不同材料；回答不吻合原表时标为人工确认。 |
| 未成年 E | 是否在读？与谁同行：独自、一位家长、双方家长或其他监护人？监护关系如何证明？相关家长／监护人是否在中国？ | 第 13 项的在读证明、亲属／监护关系证明及按同行情形确定的出行同意文件。原表没有说明所有非典型家庭结构的处理办法，不能自行推断。 |
| 多国 F | 国家间使用飞机、火车还是汽车？相应预订情况？ | 第 5 项增加适用的申根境内交通预订。 |

问答全程在 ChatGPT 对话中完成，自建 MCP App 不承载问卷。无论逐题回答还是整段描述，都使用同一套决策树状态和答案接口。MCP 的返回值始终明确下一步，最终才交接给材料工作台。

### XState 选型与执行约定

采用 [XState](https://github.com/statelyai/xstate) 作为决策模型的执行引擎，当前锁定 5.33.2。选型依据是成熟的 JavaScript／TypeScript 生态、MIT 开源许可，以及显式节点跳转、运行检查和状态建模能力。默认导出可离线查看的 HTML、SVG、Mermaid 图，并导出可供 MIT 开源 [Stately Sketch](https://github.com/statelyai/sketch) 使用的完整机器代码；执行和排查流程均不依赖付费平台。当前阶段优先保证结构清晰和可维护性，性能优化后置。

模型以问题和回答分支组织。使用 XState 原生的 `states`、跳转目标和命名 `guards` 表达节点及连接关系；问题定义和任务引用作为关联元数据保存。可序列化的结构配置按版本保存，条件函数在代码中注册并复用。图由同一份模型生成；布局变化不改变业务判断。节点 ID 保持稳定，便于关联历史记录与图上位置。

材料叶子引用稳定的任务 ID。同一个任务 ID 可以出现在多个独立叶子中，节点保留各自的父级与判断路径。根据适用分支收集任务、按任务 ID 去重并保持原表顺序，形成一位申请人的清单。第二阶段的材料处理代码按任务类型复用。问题树是流程结构的来源，不再另行维护一套从任务倒推全部适用条件的业务规则。

每次求值使用提交的完整结构化答案，从模型入口推进。逐题提交和整段事实提交遵循同一套逻辑；已有明确答案的节点可自动通过，缺少答案时返回问题，矛盾或无法覆盖的情况返回澄清／阻断要求。修改答案后根据新快照从入口重算，并处理失效分支产生的任务，不能只沿旧节点继续。未回答不等于否，也不能自动进入默认业务分支。

GPT 根据问题目录和选项定义，将自然语言归一成标准字段；服务端校验后再交给引擎。无法确定归属的情况先追问。新协议返回完整 `answers`、`revision`、`questionCatalog`、`decision` 和有明确类型的 `nextAction`，到达完整结果后交接材料 App。旧问答接口已删除，接口清单见 [MCP 接口说明](mcp-api.md)。

### 结构化输入回放与路径检查

创建申请和每次保存答案时，在该申请的 `evaluations` 中保存独立记录，以申请 ID 与求值 ID 关联，包括完整答案快照、规则版本及模型指纹、条件函数实现的构建指纹、XState 版本、输出问题／任务和节点执行轨迹。按完整快照记录求值及问答版本，回放使用当次完整快照。读取状态会即时重算，但不会重复追加历史；选择材料也不会产生新的答案历史。旧申请在升级前没有保存的输入历史无法补回，之后保存答案开始记录。

通过 XState 的 [Inspection API](https://stately.ai/docs/inspection) 捕获事件与逐步跳转，在公共条件函数中记录条件名称、判断输入及结果，转换成可持久化的业务记录。回放工具加载相同模型和执行逻辑，用已保存的结构化输入重新运行，在图中标出实际路径和停留节点，比较问题与任务输出。需要历史执行逻辑时保留对应发布构建；不能用最新条件代码冒充旧版回放。

回放不重新调用 GPT，不要求记录聊天原文。判断函数使用固定输入和版本化实现；外部查询结果或参考日期如参与决策，也应成为可保存的输入。执行记录用于检查模型是否按输入走对分支，不用于判断 GPT 是否正确理解了未保存的原话。

实施验收覆盖：相同模型生成结构图并运行；缺失答案返回问题；整段输入自动推进；多个叶子汇总且任务去重；更改答案后旧分支失效；保存输入后重跑结果一致，且每次自动跳转都能在轨迹中定位。

### 历史条件求值实现与兼容

0.4.1 把问题组、停止条件和任务条件放在版本化 JSON 中，用 `json-logic-js` 判断条件。程序按顺序扫描适用的问题组，遇到缺失答案就返回问题，适用问题全部答完后筛选材料任务。它没有显式的父子节点与跳转关系；此前称为「叶子节点」的是 `tasks_ready` 结果状态，并非树节点。0.5.0 已用 XState 节点跳转替换运行逻辑；JsonLogic 仅作为开发依赖保留在冻结的对照测试中。

新申请使用 `iceland-tourism-user-checklist-2025-03-06-xstate-1`。旧规则文件不改写，已有申请保留原 `ruleVersion`，经校验原文件 SHA-256 的兼容映射使用等价 XState 模型运行。修改旧文件会阻断兼容加载，不能悄悄用变更后的条件解释旧记录。模型与图的使用方法见[决策图与回放说明](decision-graph/README.md)。

本表至少包含以下分支：

```text
中国居住者赴冰岛旅游？
├─ 否／无法确定 → 不生成本路径清单；说明待核实条件
└─ 是
   ├─ 成人 → 在职／退休／无业
   │           └─ 无业 → 婚姻状态、收入及担保人类型
   └─ 未成年人 → 在读及监护关系、独自／单方家长／双方家长同行

以上分支确定第 11 或 13 项；另根据多国行程追加第 5 项的境内交通材料。
路径走完后，将第 1–10 项中适用的共通文件任务与条件文件任务合并，得到唯一的个人任务队列。
```

目标模型中，各问题的适用回答沿显式分支导出材料任务叶子，命中的任务合成个人清单。每个任务应关联导出它的节点路径、条件和 PDF 条目，方便解释「为什么有这一项」。重复引用同一个任务不会要求复制材料处理代码，汇总时同一个文件任务只生成一项。

例如「中国公民、居住中国、冰岛单国旅游、成年在职」得到第 1–10 项中适用的共通材料加第 11 项在职材料；若改为多国行程，第 5 项增加境内交通材料；若改为未成年人，仅重新计算受年龄与监护条件影响的材料。未回答的条件保持未确定，不进入任何最终叶子。

### 从新 checklist 生成问题树

用户提供新的 checklist 后，先提取每条材料的适用条件、所需文件、例外和出处；再归并重复条件，形成最少必要问题及其可选答案；随后检查各答案组合是否能得到明确结果，以及是否存在矛盾、空白或无法判断的分支。生成的是**待审核的规则配置草案**，人工核对原文后才发布到 MCP 服务端。PDF 没写清楚的情况标为待核实，不由模型填空。每次发布新增配置版本并切换 `active.json`；旧申请保持原版本，旧配置文件保留，不原地修改。

### 路径出口

- 非旅游目的（例如志愿活动）不套用旅游清单。原表第 12 项虽列出志愿活动邀请函，但应另建路径核对；本模拟在此停止个性化清单。
- 非中国国籍、非中国居住地、冰岛并非应受理目的地，或行程条件无法判断时，先显示需要核实的问题；不套用面向中国护照持有人居住中国的模拟路径。
- 签证是否必要、具体受理中心及官方递交办法不由这张材料表单独确定；模拟时将其列为正式申请前的核对点。

## 3. 原表到文件任务的映射

原表编号用于追溯依据，不等于任务编号。原表第 11 项的「雇主营业执照复印件」和「在职证明」是两个文件任务；第 13 项的学生证、学校证明和关系公证书也分别成任务。同一任务可以复用后续的材料处理流程。

## 4. 两阶段之间的交接

第一阶段输出的是有顺序的任务队列。每个任务至少包含：稳定的任务 ID、文件名称、对应的原表条目、命中的条件、原始要求、建议处理流程类型，以及「待处理／待核实」状态。它不包含已生成文件，也不预设用户一定要上传或自动生成。

第二阶段逐个消费任务。每个任务的目标是关联一个最终文件，并记录完成状态；如果原表还要求出示原件、打印或签字，这些作为该文件的递交说明保留，不误写成「系统生成了原件」。文件如何取得、填写与检查属于后续独立流程。

## 5. 模拟申请的验收场景

先使用虚构人物完成第一阶段：**中国公民、居住中国、成年在职、仅赴冰岛旅游**。用户一次回答基础问题与在职分支，系统生成第 1–11 项中适用的文件任务，其中营业执照复印件与在职证明是不同任务；不出现第 12、13 项。修改为「无业、由非配偶担保」后，任务队列相应变化。第二条短场景验证「未成年人仅随一位家长出行」能出现第 13 项的条件任务。

第一阶段跑通后，再选一个任务设计和验证第二阶段的材料处理流程。模拟全过程使用虚构资料，不提交官方申请。
